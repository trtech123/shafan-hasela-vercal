# Rivhit technical readiness: read-only probe and local verification

## Production connection

The deployed accounting endpoints either issue documents or execute payment workflows; none exposes a fixed read-only Rivhit company/chart/journal check using the Production secret. Supabase's secret inventory shows `RIVHIT_API_TOKEN` exists but does not reveal its value. Therefore token validity, company identity, account cards, sort codes and journal-report permissions remain unverified.

`rivhit-connection-check` is prepared locally as an isolated temporary Edge Function. It accepts only three fixed service-role requests: `POST {"mode":"identity"}` reads `Company.Details`; `POST {"mode":"catalog","expected_company_id":<verified ID>}` reads `Company.Details`, `Accounting.SortCodeList` and `Customer.List`; and `POST {"mode":"journal","expected_company_id":<verified ID>,"date":"YYYY-MM-DD"}` reads `Company.Details` and `Accounting.JournalsReport`. A company-ID mismatch stops before chart or journal reads. Gateway JWT verification is enabled. The function reads its Rivhit token only from the Edge environment. The Rivhit API uses POST even for these read operations. The request cannot choose an endpoint or pass arbitrary provider fields. Provider messages, customer names, contact details, full journal rows and tokens are never logged or returned. Only company identity, sort codes, limited numeric card references, and minimal matching journal identities are returned to the service caller. The journal search is limited to one supplied date, Payper document `200002` or its payment ID, and amount `4.00`; a zero-match response proves absence only for that searched date. `Customer.List` is a customer/card list, not a confirmed full general-ledger chart, so Anat may still need to identify revenue, VAT and clearing accounts.

The official endpoint contracts are:

- https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help/operations/GetCompanyDetails
- https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help/operations/SortCodeList
- https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help/operations/GetCustomerListByType
- https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help/operations/JournalsReport

## Disposable PostgreSQL verification

`node scripts/rivhit/rehearse-bookkeeping.mjs` starts native PostgreSQL on loopback in an isolated temporary directory, loads only the new migration, runs the nine SQL assertions, launches eight concurrent service-role claimants, and verifies exactly one winner. It then verifies that the receipt leg waits for an invoice success and that an uncertain second leg remains `reconciliation_required` while the first stays `succeeded`. It uses synthetic identifiers, no Production connection and no provider requests. The script cleans up its own temporary database.

The full Vitest suite must run with dummy `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`; this is needed for an unrelated quote test import. The bookkeeping and read-only probe tests use mocks.

## Production migration findings and safe release path

Read-only `supabase db query --remote --read-only` returned `42P01` for `supabase_migrations.schema_migrations`. A follow-up read of `information_schema.schemata` showed no `supabase_migrations` schema. `supabase migration list --remote` returned local filenames and empty remote version fields; it is not evidence that Production schema is empty. Targeted read-only schema checks found all four footprints of the duplicate-version migrations present: `physical_terminal_devices`, `physical_payment_intents`, `guard_order_delete()`, and `guard_order_archive_change()` plus `orders.archived_at`. The new bookkeeping tables are absent. This confirms the relevant structures exist but does not prove exact historical file contents or a migration ledger.

The repository contains two distinct SQL files at each of `202611120001` and `202611120002`, plus an older duplicate `202611020001` (`cafeteria_product_categories` and `pos_pelecard_intents`). Do **not** use `supabase db push` from this repository: without a Supabase migration ledger it could try to replay many existing migrations, and duplicate version names are ambiguous. For a future approved release, first capture the Production schema fingerprint and compare the new migration's object names with `to_regclass`/`to_regprocedure`. Then apply **only** `202611150001_rivhit_bookkeeping_sync.sql` as one reviewed transaction with a 5-second lock timeout and a 2-minute statement timeout. Verify the new objects and grants afterward; record the file checksum and applied timestamp in the release record. Do not create or repair a historical `supabase_migrations` ledger as part of this pilot. Resolving the duplicate filenames for future CLI migration management requires a separate inventory and reviewed repository cleanup. No Production migration was run here.

The reusable read-only preflight is `scripts/rivhit/preflight-bookkeeping-release.sql`, run with `npx supabase db query --file scripts/rivhit/preflight-bookkeeping-release.sql --remote=divzxsynczeifkpnpupl --profile supabase --read-only --output-format json`. On 2026-11-15 it returned all new source/leg/RPC objects absent, all four historical footprints present, and the Supabase migration schema absent. The SQL file itself contains `BEGIN`/`COMMIT`; an approved future release must apply that one file only after the preflight still matches.

## Shared-source parity

The local copies of `payment-edge-runtime.ts`, `payment-store.ts`, `payment-types.ts`, `rivhit/client.ts`, `rivhit/supabase-repository.ts`, and `rivhit/workflow.ts` match the active `pelecard-callback` bundle, but differ from one or more versions embedded in the active payment worker and other Rivhit bundles. The Payper issuance v82 source restoration was separately recorded in commit `c9e1fc255b105ec0833820ff0c622f8c83d4777c`. Both new Rivhit functions import only their own dedicated `_shared/rivhit-*` modules. Deploying either new function cannot rebuild Payper or Pelecard bundles. Any future deployment of an existing payment function still requires function-specific shared-source reconciliation and regression tests; a blanket replacement with the local `shared` directory is unsafe.
