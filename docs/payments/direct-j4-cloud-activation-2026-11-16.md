## Candidate flow

The cashier's eventual direct action reserves a server-priced payment for the selected order. The existing unique request key and one-unresolved-intent-per-register lock prevent duplicate clicks and concurrent terminal sends. A cloud cron invocation claims the reserved direct intent once and POSTs J4 with the validated amount, `shopNumber: "004"`, `paramX` equal to the intent ID, and empty card fields. With `PELECARD_PHYSICAL_DIRECT_PAYPER_ENABLED=true`, the request also includes the existing frozen order invoice lines, customer details and VAT decision as `PayperParameters`. The first response is reduced to an allowlist and saved before the worker changes the intent to pending. It includes provider identifiers, approval fields, amount, Payper status, number, link and document IDs when supplied. Opaque card data and raw provider responses are discarded.

The existing independent `CheckGoodParamXEMV` and `GetTransDetailsEMV` lookup validates amount, merchant terminal, register and provider identifiers before the existing atomic finalizer creates a sale and updates the existing order. The first-response invoice is associated through the one-document ledger only after verified payment and sale, with matching transaction and amount. Invoice failure keeps the payment and sale while retaining a reconciliation hold. A timeout or interrupted response remains uncertain. Recovery performs lookup and finalization only; it never sends J4 again and never calls `CreatePayperInvoice` automatically.

The cloud candidate uses the existing Vercel project, a protected minute cron route, direct physical credentials, and the existing database. It is disabled unless `PELECARD_PHYSICAL_CLOUD_WORKER_ENABLED=true`; financial dispatch has its separate existing gate. The route requests 360 seconds, leaving margin over the J4 five-minute provider timeout. The cron response reports processed, failed and unresolved counts; the database retains intent state for recovery and audit.

## Operational feasibility review — 16 November 2026

Read-only inspection of the actual Vercel project `shafan-hasela-vercal` under `TRTech's projects` found **Pro**, **Fluid Compute enabled**, and a **300-second project default**. The project Functions settings explicitly permit a per-function `maxDuration` override; `360` is within the Pro limit. The candidate's `app/vercel.json` specifies `360` for `api/pelecard-physical-worker.js` and `* * * * *` for one cron. Pro supports minute-level cron, and cron uses the target function's duration limit. The currently verified hosted source `641c373` and later cashier fix `c31c9a4` have no cron entry and retain 30-second limits on their existing physical HTTP routes. The J4 cron therefore exists **only in the candidate source**, not in the current production deployment. The candidate Git preview `CJoV5RFoJ` was blocked by the project's preview deployment policy (Git preview deployments are disallowed), so no deployed 360-second worker or scheduled run has been verified. Do not infer runtime success from the dashboard limit.

The J4 provider request uses a 300-second HTTP timeout. A 360-second function leaves at most 60 seconds for cold start, database operations, first-response persistence and independent verification. If the function ends during or after the provider call, the claimed intent must be treated as uncertain and reconciled; the worker must never send J4 again. A controlled, nonfinancial deployment rehearsal must confirm the compiled function's duration, connectivity, logs and recovery behavior. Vercel cron can overlap a prior run, miss a run or invoke a run twice; the existing atomic intent claim prevents another J4 send, and monitoring must detect stale intents. [Vercel duration](https://vercel.com/docs/functions/configuring-functions/duration), [cron delivery and overlap](https://vercel.com/docs/schedules/cron-jobs/manage-cron-jobs).

**Cashier verdict: no-go for the current cron-only candidate.** Reservation finishes on Pay, but J4 dispatch begins at the next cron invocation: nominal delay is 0–60 seconds plus scheduler jitter, function startup and database work, with no hard upper bound when a run is missed. It does not meet Nurit's requirement that the amount appear promptly on the CT20. This is a timing issue even though the function duration and cron frequency fit the plan.

The smallest viable architecture on the existing Pro account is an immediate, **durable** trigger after the server commits the priced intent: a transactional outbox/queue record keyed by payment ID, an acknowledged cloud enqueue, and a 360-second consumer that atomically claims the intent before its single J4 call. The cashier receives the reservation/enqueue acknowledgement promptly and polls the existing status endpoint; cron performs recovery and monitoring only. A queue delivery may repeat, so the database claim remains the financial idempotency boundary. If enqueue fails, retain the reserved intent and show a recoverable waiting/error state; do not claim that the terminal was sent. Before choosing a trigger, verify its availability, security, delivery guarantee, 360-second consumer support and charges on this team. No queue or paid service was provisioned in this branch. A browser-launched, unawaited worker request or `waitUntil` without an acknowledged durable queue is not an acceptable financial trigger. Until an immediate trigger is implemented and rehearsed, keep the direct cashier and dispatch gates off and use hosted EMV.

Integration baseline: this branch is based on `641c373`; terminal 1's later `99ae1b6` and `c31c9a4` add billing-email fallback, cash/check capability gating and stalled digital-checkout handling. They touch `CashRegister.jsx`, `PaymentScreen.jsx`, the noncard Edge Function and a migration. Merge/rebase onto terminal 1's **final verified production source** before any direct cashier wiring. Preserve those gates and the hosted EMV path. This branch has not changed the cashier page or production settings.

Read-only monitoring query after the migration:

```sql
SELECT i.payment_id, i.register_number, i.state, i.amount_minor,
  i.verified_amount_minor, i.dispatch_started_at, i.updated_at,
  i.first_response->'document'->>'state' AS first_document_state,
  l.state AS ledger_state, l.document_number
FROM public.physical_payment_intents i
LEFT JOIN public.payper_document_ledger l ON l.payment_id=i.payment_id
WHERE i.route='direct' AND (
  i.state IN ('uncertain','approved')
  OR (i.state='reserved' AND i.created_at < now()-interval '2 minutes')
  OR (i.state IN ('dispatching','pending') AND
      i.dispatch_started_at < now()-interval '6 minutes')
  OR (i.state='succeeded' AND l.state='source_blocked'))
ORDER BY i.created_at;
```
