## Candidate flow

The cashier's eventual direct action reserves a server-priced payment for the selected order, then awaits acknowledgement of a Vercel Queue message containing only the payment ID. The existing unique request key and one-unresolved-intent-per-register lock prevent duplicate clicks and concurrent terminal sends. The private queue consumer atomically claims the reserved direct intent once and POSTs J4 with the validated amount, `shopNumber: "004"`, `paramX` equal to the intent ID, and empty card fields. With `PELECARD_PHYSICAL_DIRECT_PAYPER_ENABLED=true`, the request also includes the existing frozen order invoice lines, customer details and VAT decision as `PayperParameters`. The first response is reduced to an allowlist and saved before the worker changes the intent to pending. It includes provider identifiers, approval fields, amount, Payper status, number, link and document IDs when supplied. Opaque card data and raw provider responses are discarded.

The existing independent `CheckGoodParamXEMV` and `GetTransDetailsEMV` lookup validates amount, merchant terminal, register and provider identifiers before the existing atomic finalizer creates a sale and updates the existing order. The first-response invoice is associated through the one-document ledger only after verified payment and sale, with matching transaction and amount. Invoice failure keeps the payment and sale while retaining a reconciliation hold. A timeout or interrupted response remains uncertain. Recovery performs lookup and finalization only; it never sends J4 again and never calls `CreatePayperInvoice` automatically.

The cloud candidate uses the existing Vercel project, a private queue consumer, a protected minute cron recovery route, direct physical credentials, and the existing database. It is disabled unless `PELECARD_PHYSICAL_CLOUD_WORKER_ENABLED=true`; financial dispatch has its separate existing gate. The queue consumer requests 360 seconds, leaving margin over the J4 five-minute provider timeout. Cron never dispatches a reserved intent. The cron response reports processed, failed and unresolved counts; the database retains intent state for recovery and audit.

Read-only monitoring query after the migration:

```sql
SELECT i.payment_id, i.register_number, i.state, i.amount_minor,
  i.verified_amount_minor, i.dispatch_started_at, i.updated_at,
  i.first_response->'document'->>'state' AS first_document_state,
  l.state AS ledger_state, l.document_number
FROM public.physical_payment_intents i
LEFT JOIN public.payper_document_ledger l ON l.payment_id=i.payment_id
WHERE i.route='direct' AND (
  i.state IN ('uncertain','approved')
  OR (i.state='reserved' AND i.created_at < now()-interval '2 minutes')
  OR (i.state IN ('dispatching','pending') AND
      i.dispatch_started_at < now()-interval '6 minutes')
  OR (i.state='succeeded' AND l.state='source_blocked'))
ORDER BY i.created_at;
```
