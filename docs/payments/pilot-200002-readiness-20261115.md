## Rivhit chart and duplicate search

Rivhit's [Customer.List contract](https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help/operations/GetCustomerListByType) supports `customer_type` and `filter_fields`, but documents no pagination. Its [customer guide](https://rivhit-api.readme.io/docs/how-to-locate-a-customer) says account tickets are represented as customer types, with income/expense tickets generally in types 40–59; type IDs can vary by account. [Customer.TypeList](https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help/operations/GetCustomerTypeList) discovers actual types. [Customer.Get](https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help) can fetch a known ID. No dedicated general-ledger chart-list operation appears in Rivhit's [published operation list](https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help). Thus `Customer.List` with a discovered accounting type is the first bounded option; do not request type 1 or an unfiltered full customer list. Return only ID, type and external account reference from a short allowlist. If a filtered response still exceeds the cap, cancel the stream at a fixed byte limit and request the few relevant account IDs from Anat; do not retain or log customer rows. The `filter_fields` names and semantics need supplier confirmation before use.

Rivhit's [Accounting.JournalsReport](https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help/operations/JournalsReport) takes a date and returns a daily journal, with no server-side reference or account filter. [Customer.JournalReport](https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help/operations/GetCustomerJournalReport) supports a known `customer_id` and year, and is useful after the relevant account IDs are identified. The prior 09.11.2026 daily call failed; it must be retried with bounded backoff and timeout. A safe follow-up should separately match `200002` and the payment ID across both references and details irrespective of amount, and inspect 4.00 ILS candidates without treating them as proof. Do not return full journals or personal data. The previous negative searches cannot exclude an aggregated or manually referenced posting. A second, accountant-led search in Rivhit remains the final duplicate check before any first transfer.

The removed temporary function has been **updated locally only** for a separate approval: `account_cards` accepts one company-confirmed `customer_type` in the fixed 40–59 range; responses expose only card ID, type and `acc_ref`. The provider body reader now cancels after 2 MB even if `Content-Length` is absent. The journal mode now searches references and details irrespective of amount, returns at most 20 stripped matches plus counts, and can be used for the 09.11 retry. It has **not** been redeployed or invoked against Production. A new, narrow authorization would be needed to deploy this revised function, call it for selected accounting types and 09.11, and delete it again. Type 1 customer records and arbitrary provider operations remain outside its allowlist.

## Local intake protection and remaining work

The draft migration now contains a separate `rivhit_bookkeeping_intake` and a service-role-only capture RPC. It reads only `succeeded` Payper ledger rows joined to `succeeded` payments, and holds each captured identity as `held_evidence`; unique constraints cover ledger ID, payment ID and document number. An application flag **and** database control are both off by default. Repeated capture returns the same intake ID. It does not touch legacy `accounting_events`, create a bookkeeping leg, or call Rivhit. A separate observer module calls the RPC only for a successful Payper outcome and treats capture errors independently from Payper issuance. It is not yet wired to a deployed worker. Future wiring should be a separate observer that scans the durable Payper success ledger, so no Payper/Pelecard production bundle needs rebuilding.

Before first pilot: obtain the issued Payper document details, retrieve/confirm the relevant Rivhit account IDs and 09.11 journal, have Anat approve each posting field and duplicate absence, reconcile the historical migration names, review/apply the new migration separately, deploy only the new observer/worker under a separate release approval, then authorize one explicitly identified transfer. Current Production sync stays disabled.
