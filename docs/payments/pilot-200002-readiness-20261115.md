## Rivhit chart and duplicate search

Rivhit's [Customer.List contract](https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help/operations/GetCustomerListByType) supports `customer_type` and `filter_fields`, but documents no pagination. Its [customer guide](https://rivhit-api.readme.io/docs/how-to-locate-a-customer) says account tickets are represented as customer types, with income/expense tickets generally in types 40–59; type IDs can vary by account. [Customer.TypeList](https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help/operations/GetCustomerTypeList) discovers actual types. No dedicated general-ledger chart-list operation appears in Rivhit's [published operation list](https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help). The approved probe requested each type 40–59 separately, returned only keyword-matched account labels and identifiers to the authorized service caller, and cancelled oversized responses at a fixed 2 MB limit. `filter_fields` names and semantics still need supplier confirmation before use.

Rivhit's [Accounting.JournalsReport](https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help/operations/JournalsReport) takes a date and returns a daily journal, with no server-side reference or account filter. The authorized retry for **09.11.2026 failed three times** (function response HTTP 502), so that day remains unchecked. [Customer.JournalReport](https://api.rivhit.co.il/online/RivhitOnlineAPI.svc/help/operations/GetCustomerJournalReport) was read for 26 relevant candidate cards: 14 succeeded, covering 1,474 rows in 2026, with **zero** matches for `200002`, `RCP-1026` or the linked payment ID in references/details; 12 failed (function HTTP 502). These negative results cannot exclude an aggregated, differently referenced or manually posted entry, nor any failed card report. An accountant-led search in Rivhit and resolution of the failed daily report remain the final duplicate checks before any first transfer.

The temporary function was deployed only for the approved reads and then removed. Its final Production inventory count was zero. Before every card/report request it rechecked company identity. All types 40–59 returned filtered card lists; 26 descriptions matched the restricted accounting-keyword filter. The response reader enforced a 2 MB cap, and no full customer or journal responses were returned or logged. Type 1 customer records and arbitrary provider operations were outside its allowlist.

## Local intake protection and remaining work

The draft migration now contains a separate `rivhit_bookkeeping_intake` and a service-role-only capture RPC. It reads only `succeeded` Payper ledger rows joined to `succeeded` payments, and holds each captured identity as `held_evidence`; unique constraints cover ledger ID, payment ID and document number. An application flag **and** database control are both off by default. Repeated capture returns the same intake ID. It does not touch legacy `accounting_events`, create a bookkeeping leg, or call Rivhit. A separate observer module calls the RPC only for a successful Payper outcome and treats capture errors independently from Payper issuance. It is not yet wired to a deployed worker. Future wiring should be a separate observer that scans the durable Payper success ledger, so no Payper/Pelecard production bundle needs rebuilding.

Before first pilot: Anat must identify/approve the revenue, VAT, customer and card-clearing accounts and sort codes; choose the posting structure, date, period and target report; and establish no earlier posting for `200002`, `RCP-1026` or the payment ID despite the unresolved 09.11 report and 12 failed card reports. The historical migration names still require reconciliation. Applying any migration, deploying the new observer/worker or transferring the first journal needs separate approval. Current Production sync stays disabled.
