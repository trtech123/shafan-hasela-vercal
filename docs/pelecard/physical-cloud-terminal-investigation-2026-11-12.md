## Admin-controlled physical device settings

The dedicated `/physical-terminal-settings` page manages four fixed rows: `003` N86 and `004`–`006` CT20. Register numbers are strings throughout storage, APIs and provider requests; leading zeroes must be preserved, and numeric `3` is invalid. An admin can edit the device label, assign one existing named `cash_registers` workstation, and mark the device enabled or disabled. An admin can create a named cash register from the same page. Device numbers and models are immutable in the admin API; one workstation cannot be assigned to two devices. All devices start disabled. The database RPCs require the authenticated admin role, while the service role has read-only access for the future physical adapter. No API user, password, card details, or digital terminal settings appear on the page or in the new table. Physical API credentials remain separate server secrets.

Device `enabled` is an assignment readiness setting. It cannot override the independent `PELECARD_PHYSICAL_ENABLED` and `PELECARD_PHYSICAL_DISPATCH_ENABLED` runtime gates, both disabled by default. The physical resolver reads only an enabled device assigned to an active named cash register; it never accepts a register number from the browser. The page does not yet bind a browser to a named cash register, and the live checkout still cannot dispatch. The new migration has been exercised only in disposable local PostgreSQL; it has not been applied to Production.

## Planned isolation and guarantees

The new method uses a separate physical intent, provider adapter, credentials, workstation-to-register mapping and disabled-by-default flag. A server-only mapping selects the register; the client cannot override it. Catalog prices are recalculated on the server and frozen before a dispatch attempt. The POS automatically sends that validated amount to the assigned terminal. The cashier never enters the amount on the physical device. The selected terminal must display the exact sent amount before the customer taps or inserts a credit card into the device; dispatch acknowledgement alone is not payment approval. The device handles card reading and EMV/PIN interaction. The POS sends no raw card fields and stores none. A durable unique request key and an atomic register lock allow one dispatch per intent and one in-flight intent per device. Any send timeout or ambiguous response remains unresolved until an authenticated provider lookup proves a final result. The system receives the payment outcome and verifies it with Pelecard's authoritative lookup. A verified approval must match merchant terminal, register, amount, intent reference and provider transaction ID before an atomic database finalizer saves exactly one POS sale and makes that verified payment eligible for the existing Payper invoicing pipeline in the same transaction. The pipeline must automatically issue exactly one Invoice-Receipt and email it to the verified customer address. Repeated and concurrent verification must return the same sale; a unique provider transaction identity and a unique sale-to-intent relationship must be enforced in the database. Declined, cancelled or uncertain payments cannot enter Payper. Existing Payper one-shot ledger rules must be used via a separate physical adapter; the continuous digital worker and credentials remain unchanged. Duplicate document checks must include the provider transaction identity and all existing sale/order document sources. An uncertain Payper creation or email result requires reconciliation, never blind reissuance.

The physical configuration requires a separately supplied ten-digit `PELECARD_PHYSICAL_TERMINAL`; tests use the photographed `2814926015`. It never reads digital terminal credentials. The mocked workflow accepts a provider-approved result only if full terminal, register, amount, intent and transaction ID correlate. A correlated final decline can release the intent; a timeout or mismatched lookup remains uncertain and is never blindly resent. The current strict real lookup parser recognizes approval only; the concrete provider decline shape still needs confirmation. A flag-gated cashier component renders waiting, uncertain, declined and approved states; its uncertain state only offers status inspection, not another charge. The branch has the J4 transport and database finalizer but does **not** yet have a deployed long-lived worker, physical Payper adapter, or live POS action. No live payment or invoice has been attempted.
