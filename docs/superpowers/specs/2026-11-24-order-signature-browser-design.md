# אישור הזמנה וחתימה בדפדפן

## מצב קיים

בייצור יש מסלול PDF ישן ב־OrderConfirmationPDF לצד מסלול גרסאות חתימה. שליחת WhatsApp הישנה שולחת PDF ישירות; מסלול הגרסאות יוצר PDF פרטי וקישור, אך גם שולח PDF כקובץ מצורף. הכפתור „הכנת אישור לחתימה” יוצר גרסה, PDF וקישור, ואינו שולח. הטופס הציבורי מציג PDF ומאפשר כרגע שם וחתימה בלבד. מזהה חותם אופציונלי בשרת אך אינו נשלח מהממשק. תיקון ה־401 של Edge מבוסס JWT עובד לפי חוזה הקוד, אך נדרשת בדיקת Production שאינה שולחת מסמך לפני שחרור.

## תכנון

1. לאחר שמירת הזמנה חדשה, הממשק מבקש הכנת גרסה דרך API קיים. הצלחה מדווחת רק לאחר שהאישור מוכן; כשל הכנה מציג שההזמנה נשמרה אך האישור טרם מוכן, בלי לשלוח ובלי ליצור גרסה חדשה בשקט. כרטיס האישור מאפשר הכנה מחדש מפורשת. עריכת הזמנה אינה מחליפה גרסה חתומה אוטומטית.
2. ערוץ המייל של מסלול החתימה שולח קישור לטופס בלבד. WhatsApp שמבוסס על תבנית PDF קיימת מסומן במפורש כמסלול PDF נפרד; לא משנים תבנית ספק ללא אישור. הורדת PDF והיסטוריית שליחות נשארות זמינות.
3. הטופס הציבורי מציג תקציר מוגבל של נתוני הגרסה הקפואה בתוך הדפדפן, שדות קשר חסרים, מזהה חותם אופציונלי וחתימה. PDF נשאר לצפייה לפי בקשה ואינו תנאי לחתימה. התשובה נקשרת לגרסת האישור לפי token מוגבל בזמן.
4. פרטי ההשלמה נשמרים ברשומת תגובה נפרדת ובלתי ניתנת לשכתוב. ההזמנה והגרסה מקושרות תמיד; לקוח מקושר רק אם ההזמנה כבר מקושרת; ליד מקושר רק אם קיים ליד יחיד המחובר להצעת המחיר של ההזמנה. אין יצירת ליד, אין התאמה לפי דמיון בשם ואין דריסה של פרטי כרטיס לקוח או ליד. הזמנות ללא קישור חד־משמעי מסומנות לבדיקה ידנית.
5. שמירת התגובה אידמפוטנטית לפי גרסה ובקשת חתימה. פלט PDF חתום וראיית חתימה קיימת נשמרים. מסלול ישן אינו משכתב גרסאות קודמות.

## בדיקות ושחרור

בדיקות ממוקדות יכסו שמירה בלי שליחה, הצגת תקציר בטוח, אימות שדות, replay, קישור ליד חד־משמעי, אי־שכתוב נתונים קיימים, ומסלולי PDF הוותיקים. שחרור ידרוש מיגרציה אדיטיבית, בדיקת הרשאות וגיבוי, פריסת שרת/Edge/ממשק לפי חוזה, ובדיקה ללא שליחת מסמך אמיתי.
