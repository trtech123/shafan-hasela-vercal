# Rivhit Bookkeeping Sync Implementation Plan

> תכנון מותנה באישור מסלול האינטגרציה והמיפוי של ענת. אין לבצע כעת אף סעיף המסומן כשלב מימוש.

**Goal:** קליטת הרישום החשבונאי של מסמכי המקור והעסקאות ברווחית, בלי להפיק מסמך נוסף ובלי לפגוע בסליקה או ב־Payper.

**Architecture:** Outbox נפרד לכל מסמך מקור מאומת; mapper עם גרסת מיפוי מאושרת; worker ייעודי לרישום פקודות יומן או ליצוא קובץ; reconciliation אחרי כל תוצאה לא ודאית. תור הפקת רווחית הישן נשאר מוחזק.

**Tech Stack:** React/Vite, Supabase PostgreSQL ו־Edge Functions, Payper/Pelecard, Rivhit Online API או יבוא קובץ מאושר.

ראו [מסמך התכנון](../specs/2026-11-15-rivhit-bookkeeping-sync-design.md) לממצאי Production, חוזה הנתונים ומקורות הספקים.

## שער 0 — הכרעה חשבונאית וטכנית, ללא כתיבה חיה

- [ ] ענת מאשרת סוג הנהלת חשבונות, חשבון החברה, דוח היעד, מבנה שתי הפקודות למסמך חשבונית־קבלה 200002, קודי מיון, כרטיסי חובה/זכות, טיפול במע״מ, תאריך אסמכתה, לקוח, אמצעי תשלום ועיגול. מתעדים דוגמת פקודה מלאה עם נתוני פיילוט בלבד בערוץ מאובטח.
- [ ] רווחית מאשרת שהחשבון וה־token הקיים מורשים ל־`Accounting.AddJournal` ולקריאות הדוח, שמות השדות וגבולותיהם, משמעות `request_reference`, דרך איתור פקודה אחרי timeout, מגבלות קצב וסביבת בדיקה. מאמתים הרשאה באמצעות קריאות metadata/report בלבד; אין לקרוא `AddJournal` בשלב גילוי.
- [ ] אם API אינו מתאים: ענת ורווחית מאשרות פורמט קובץ פקודות יומן, מי מייבא אותו, איך שומרים אסמכתת Payper ואיך מזהים קליטה כפולה. מתעדים החלטה מפורשת API/קובץ.
- [ ] Payper/Pelecard מאשרים דרך קריאה נתמכת למסמכי מקור, מסמכי זיכוי ומסמכי מזומן/המחאות אם הם זמינים. אין ליזום סליקה או הפקת מסמך לצורך הבדיקה.
- [ ] משווים את כל חבילות ה־Edge הפעילות לקוד הענף. עבור `_shared` שיש לו כמה גרסאות פרוסות, בוחרים עותק בסיס לפי הפונקציה שתשתנה, מבצעים contract tests, ומוודאים שלא תיפרס חבילה מעורבת. שומרים fingerprint של Vercel ושל Edge לפני שינויים.
- [ ] מיישבים את כפילות מזהי ה־migration הקיימת בענף המקור (`202611120001` ו־`202611120002` משמשים כל אחד שני קבצים שונים) מול היסטוריית Production לפני כל migration חדשה. אין להריץ מחדש, לשנות בשם או להניח שכולם הותקנו.

## שער 1 — תשתית סנכרון מנותקת

**קבצים:** להוסיף `supabase/migrations/202611150001_rivhit_bookkeeping_sync.sql`, בדיקת SQL מקבילה ב־`supabase/tests/`, ואת `supabase/functions/_shared/rivhit-bookkeeping/{source,mapper,repository,client,reconciliation,worker}.ts` עם בדיקות יחידה נפרדות. להוסיף `supabase/functions/rivhit-bookkeeping-worker/index.ts` עם מתג שרת כבוי כברירת מחדל.

- [ ] מגדירים טבלת מקור מוקפא, טבלת רגלי יומן, תור ניסיונות ויומן התאמות. מפתח ייחודי כולל חשבון רווחית, מערכת מקור, מזהה מסמך מקור, סוג רגל ומספר תיקון; `request_reference` ייחודי לכל רגל. RLS מאפשר קריאה רק למנהלים מורשים וכתיבה רק לשירות.
- [ ] כותבים בדיקות SQL שמוכיחות: מקור כפול נדחה; payload hash לא משתנה; שתי משיכות מקבילות מניבות claim יחיד; שבעת אירועי `accounting_events` הישנים אינם נקראים או משתנים; ללא מסמך מקור מאומת אין `ready`.
- [ ] מממשים mapper שמקבל רק snapshot מאומת ומיפוי בגרסה מאושרת. סכומים מיוצגים באגורות עד גבול ה־API; כל פקודה מאוזנת בהתאם לאישור ענת. מבחנים כוללים סכום, מע״מ, לקוח, תאריך, מקור, אמצעי תשלום, רגל חשבונית ורגל קבלה.
- [ ] client הכתיבה מוגבל ל־`Accounting.AddJournal` אם זה המסלול שאושר. בדיקת contract דוחה כל ניסיון ל־`Document.New` או `Receipt.New`. adapter הקריאה תומך ב־`Status.LastRequest` ובדוח יומן לפי החוזה המאושר.
- [ ] worker כבוי כברירת מחדל; timeout/ניתוק אחרי אפשרות שליחה עובר ל־`reconciliation_required` בלי retry. כשל מקומי מוכח לפני שליחה בלבד רשאי לחזור. שומרים שנה/חודש/שורה רק לאחר התאמת תגובת הצלחה.

**שער יציאה:** בדיקות יחידה, SQL וחוזה עוברות בסביבה מבודדת; build עובר; אין שינוי במספר מסמכי Payper או באירועי רווחית הישנים; אין קריאה חיה לרווחית.

## שער 2 — פיילוט 200002, לאחר אישור נפרד להעברה אמיתית

**קבצים:** להוסיף כלי preflight קריאה בלבד ב־`scripts/rivhit/`, וכלי השוואת דוח ללא כתיבה. להרחיב מסך מנהל ב־`app/src/pages/AccountingOperations.jsx` או להוסיף מסך סטטוס ממוקד, בלי להכניס כפתור הפקה למסלול Payper.

- [ ] מאמתים ב־Payper ובמאגר: מזהה מסמך יציב, מספר 200002, סוג, תאריך, סכום 4.00 ש״ח, לקוח, מע״מ ומזהה תשלום `PRODUCTION_PAYMENT_ID_REDACTED`. אם שדה מהותי חסר, הפיילוט נשאר `held_mapping`.
- [ ] ענת בודקת בדוח/כרטסת רווחית שאין כבר פקודה עבור המסמך, ומאשרת את שתי הפקודות המדויקות. מבצעים dry run ושומרים hash ו־`request_reference` לכל רגל.
- [ ] רק לאחר אישור מפורש להעברה חיה: מפעילים יעד יחיד, שולחים כל רגל פעם אחת, מאמתים את תשובת `year/month/line`, מחפשים את שתי הפקודות בדוח של ענת ובודקים שאין רישום נוסף. אם רגל אחת לא ודאית, עוצרים את השנייה עד החלטה חשבונאית כדי שלא יישארו רישומים לא מאוזנים.
- [ ] חוזרים על קריאת הדוח ועל ניסיון enqueue זהה כדי להוכיח שאין פקודה נוספת. לא מבצעים סליקה חדשה ולא מפיקים מסמך Payper או רווחית נוסף.

**שער יציאה:** ענת מאשרת שהסכום והמע״מ בדוח נכונים ושהמסמך מיוצג פעם אחת מבחינה חשבונאית. שומרים אסמכתאות רווחית ודוח התאמה, בלי לשמור סודות.

## שער 3 — כניסה מדורגת של נתונים חדשים

- [ ] מפעילים enqueue רק למסמכי Payper מאומתים שנוצרו אחרי cutoff חדש. מתחילים בקופה באשראי; מוסיפים הזמנות רק אחרי בדיקת קשר מסמך־תשלום־הזמנה. שומרים watermark וקצב מוגבל.
- [ ] לכל מסלול נבדקים: מסמך מקור, מיפוי מאושר, בדיקות עיגול ומע״מ, retry בטוח, כשל ספק, השבתת worker, אי־שינוי של תשלום ושל Payper, דוח רווחית ומניעת כפילות.
- [ ] מזומן/המחאות וחוגים נשארים מוחזקים עד שיש מסמך מקור חוקי ומיפוי ענת. ביטולים/זיכויים/החזרים נכנסים רק עם מסמך תיקון וקשר למקור, כלל סטורנו ותאריך מאושרים.

**שער יציאה:** ניטור חריגים, גיל תור והפרשי ספירה; כיבוי worker עוצר שליחה בלי להשפיע על סליקה או הפקת Payper.

## שער 4 — השלמה היסטורית

- [ ] מריצים גילוי קריאה בלבד על `payment_transactions`, `sales`, `orders`, `payper_document_ledger`, מסמכי תיקון וחיובי חוגים; מצליבים מול דוח/כרטסת רווחית. כל מקור מסווג `already_recorded`, `eligible`, `needs_evidence` או `conflict`.
- [ ] ענת מאשרת תקופות, מסמכים בודדים, פקודות שכבר הוזנו ידנית, חודשים סגורים וסדר קליטה. אין להשתמש בשבעת אירועי `configuration_required` הישנים כ־backfill.
- [ ] לאחר אישור נפרד, מעבדים batch קטן לפי תקופה. משווים לפני/אחרי ספירות וסכומים לפי מקור, אמצעי תשלום, סוג מסמך, מע״מ ופקודות התאמה. עוצרים על הפרש כלשהו לפני batch הבא.

## בדיקות שימור ופריסה

- [ ] לפני מימוש: שומרים את תוצאת baseline של `npm test --prefix app -- --run`, `npm run build --prefix app`, בדיקות Payper/Rivhit ו־Edge/SQL הממוקדות. מתעדים כל כשל קיים; אין לייחס אותו לאינטגרציה החדשה.
- [ ] Preview וסביבת בדיקה בלבד עד אישור נפרד. migration additive ו־worker כבוי; בודקים hash וקוד של כל Edge Function מול הגרסה ששוחזרה לפני כל deploy עתידי.
- [ ] אחרי אישור Production עתידי: פריסה כבויה, preflight קריאה בלבד, פיילוט יחיד, דוח ענת, ורק אז cutoff לעסקאות חדשות. rollback הוא עצירת ה־worker והצגת מצב התאמה; לא מחיקה או שליחה חוזרת של פקודות שכבר הגיעו לרווחית.

**גבול השלב הנוכחי:** הכנת ענף, שחזור מקור, מסמכי תכנון ובדיקות baseline בלבד. כל סעיף שערי 1–4 ממתין לאישור מסלול האינטגרציה והמיפוי החשבונאי.
