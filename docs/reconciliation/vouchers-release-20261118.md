# Coffee voucher release group — 2026-11-18

This isolated branch starts from operational restoration commit `7614fa6dc9a991efeb18319e7358e6265e5f5ee5`. It adds order-linked voucher creation, administrator register setup, voucher list/filtering, and a downloadable informational report. It does not add automatic voucher email or accounting-document issuance. The report explicitly says it is not an accounting document or proof of payment. Protected cash, hosted Pelecard, Direct J4, Payper and order-payment routes remain unchanged.

Read-only production inspection confirmed `create_hakafa_voucher(uuid,jsonb)` and `save_cash_register(text,text,boolean)` exist as SECURITY DEFINER RPCs executable by authenticated users. The `hakafa_vouchers` and `cash_registers` tables have staff SELECT policies for admin/operations/cashier. Their internal RPC authorization and business rules remain authoritative; this structural check does not prove a successful live voucher. Local schema rehearsal includes voucher idempotency and unique order association.

The client uses an order-linked customer snapshot, explicit register choice, bounded service/contact fields, and a signature. The save has a fixed request UUID. On timeout or lost response it reads the existing order voucher and does not issue another create call. The report reads saved voucher snapshots and caps output at 500 entries. No voucher or accounting document was generated in Production.

Local verification: six focused voucher/signature/cashier files passed 19/19 tests, ESLint passed, and the production Vite build passed. After merging the operational login fix, another six-file run passed 19/19 and ESLint/build passed again. A newly found error-mapping bug was fixed: the RPC's `billing_company_id_required`, `active_register_required` and `voucher_access_denied` results now explain the known correction instead of falsely saying issuance is uncertain; three focused tests cover these messages. The client still never retries an uncertain creation. An extracted generic PDF helper is included locally so voucher reporting does not depend on the quotation-delivery release group.

## Exact business/accounting decisions still required

1. Confirm whether the signed voucher is **only an internal acknowledgement of an unpaid order**. This candidate creates no sale, payment, Invoice-Receipt or other official accounting document; its PDF explicitly states it is not one. Specify which official document, if any, is required when service is provided on credit.
2. Define the later settlement/redemption workflow: who records payment, how it links to the original order and immutable voucher, when Payper issues the official document, and how a second sale/document is prevented. This candidate deliberately implements no redemption or automatic accounting action.
3. Confirm the customer-data policy for vouchers. The current live/local schema requires a linked customer snapshot, an explicit VAT decision, contact name/phone and, for an organization, a nine-digit company ID. Optional-customer orders can still be created, but a voucher cannot be issued until those voucher-specific requirements are met. Do not invent missing identity data.
4. Confirm who may issue vouchers (current RPC: admin, operations, cashier), whether a manager must approve a credit arrangement, and whether the report's register/date/creator fields meet operational reconciliation needs.
