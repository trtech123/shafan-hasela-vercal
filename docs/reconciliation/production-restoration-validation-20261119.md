## Rollback and cleanup

- **App failure:** stop tests, preserve logs/IDs, and with release-coordinator approval point the Production alias back to the recorded prior READY deployment using the controlled manual process. Verify alias and core order/POS/payment routes. Do not automatically roll back the database, migrations or existing financial records.
- **Schema:** no migration is planned for these UI groups. If a fresh preflight finds a missing dependency, stop and prepare a separately reviewed additive migration; never apply a historical script blindly or reimpose a constraint automatically.
- **Test data:** after acceptance, review the ledger and dependencies. Archive synthetic customers where supported; unlink/deactivate test users and instructor link through authorized admin flows. Delete only truly isolated, non-audit test rows after explicit approval and referential checks. Retain immutable signature/attendance audit and private PDF evidence until a retention decision is made; never delete real records or issue compensating financial actions as cleanup.
- **Backup:** a whole-Production restore would overwrite post-backup orders, payments and invoices, and would not restore Storage bytes. It is an incident decision only, never routine rollback. Without PITR, any data loss after the backup timestamp must be assessed before a restore is considered.
